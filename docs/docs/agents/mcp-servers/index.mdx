# MCP Server Specifications

MCP (Model Context Protocol) server specifications define how agents connect to external tools and services.

## Overview

MCP servers provide tools and resources to agents through a standardized protocol. A specification
is one of two shapes:

- a **remote server** names the `url` it is reached at and the `headers` sent with every request
  (the bearer among them): the runtime connects to it over Streamable HTTP itself, no process is
  started and nothing is fetched. The Datalayer MCP server and its toolsets (`datalayer`,
  `odoo`, `odoo-accounting`, `earthdata`), Hugging Face's and Kaggle's hosted servers are remote;
- a **local server** names the `command` that runs it and its `args`: over stdio, or, with
  `transport: streamable-http` and a `url`, as a local HTTP process the runtime reaches at that
  url (`google-workspace`).

A specification names a `command` or a `url`, never neither. One that names both is a local HTTP
process.

## Required Fields

### `id` (string)
Unique identifier (kebab-case, e.g., `kaggle`, `github`, `filesystem`)

### `version` (string)
Spec version (currently `0.0.1`).

### `name` (string)
Display name shown in the UI

### `description` (string)
Server capabilities description

## A remote server

### `url` (string)
Where the server is reached, over Streamable HTTP. A query may choose what it serves: the
Datalayer gateway's `only=` asks for one toolset.
```yaml
transport: streamable-http
url: "https://mcp.datalayer.run/mcp?only=odoo-accounting"
```

### `headers` (object)
The headers sent with every request. A credential belongs in a `${VAR}` reference, expanded by
the runtime as the server starts and never written down: the runtime holds what it expanded and
withholds it from everything the model reads.
```yaml
headers:
  Authorization: "Bearer ${DATALAYER_API_KEY}"
```

A remote server names no `command` and no `args`.

### `auth` (object)
A bearer minted for the run instead of one written in `headers`. `kind` says who mints it and
`identity` names the [Identity](../../identities) the server trusts. Today one kind:
`agentcore-gateway`, an Amazon Bedrock AgentCore Gateway whose inbound authorizer trusts an
Identity issued by `aws-agentcore` that speaks `mcp` (`aws-agentcore-gateway`). The runtime asks
its identity provider for the run's inbound token and sends it as `Authorization: Bearer …`; the
spec sets no `Authorization` header of its own.
```yaml
transport: streamable-http
url: "https://<gateway-id>.gateway.bedrock-agentcore.<region>.amazonaws.com/mcp"
auth:
  kind: agentcore-gateway
  identity: aws-agentcore-gateway
```

`agentcore-gateway-example` is one, off by default: copy it with your gateway's URL. A server
with `auth` is remote (no `command`, an https `url`), and its identity is in the catalogue.

## A local server

### `command` (string)
Executable command to start the server
```yaml
command: python
command: npx
command: uvx
```

### `args` (list of strings)
Command arguments including environment variable references
```yaml
args:
  - "workspace-mcp"
  - "--transport"
  - "streamable-http"
```

A local server that listens over HTTP names `transport: streamable-http` and the `url` its
command listens at; the runtime starts the command and reaches it there.

## Optional Fields

### `transport` (string)
Transport protocol: `stdio` (a local process spoken to over its standard streams, the default)
or `streamable-http` (a remote server at its `url`, or a local command listening at its `url`).
```yaml
transport: stdio             # A local process, over its standard streams
transport: streamable-http   # Reached at its url: remote without a command, local with one
```

### `envvars` (list of strings)
Required environment variable IDs. References specs in `env-vars/` directory.
```yaml
envvars:
  - KAGGLE_API_TOKEN:0.0.1
  - GITHUB_TOKEN
```

### `env` (object)
Environment variables to set for a local server's process
```yaml
env:
  NODE_ENV: production
  LOG_LEVEL: info
```

### `sandbox_envvars` (list of strings)
Environment variables the code a server's tools write reads in the code sandbox (a download's
script): given to the sandbox when the account has them, never to the server, never required.

### `install` (object)
How the server is installed where an agent runs it: `type` says what is installed, `command`
the shell command that installs it on your own machine, `note` what else to know. Every
server of the catalogue says it; a page of the server shows it, with the command to copy.

| `type` | What is installed | `command` |
| --- | --- | --- |
| `npm` | An npm package | `npm install -g <package>` |
| `python` | A Python package, often a uv tool | `uv tool install <package>`, `pip install <package>` |
| `docker` | A Docker image | `docker pull <image>` |
| `git` | A repository built from source | `git clone … && npm install && npm run build` |
| `remote` | Nothing: a hosted server reached at its `url` | `""` |
| `built-in` | Nothing: the runtime image carries it | `""` |
| `other` | What the note says | `""` or a command |

```yaml
install:
  type: git
  command: "git clone --depth 1 https://github.com/brianellin/bsky-mcp-server ~/.local/share/mcp-servers/bsky-mcp-server && cd ~/.local/share/mcp-servers/bsky-mcp-server && npm install && npm run build"
  note: "Then `export BLUESKY_MCP_SERVER_DIR=~/.local/share/mcp-servers/bsky-mcp-server`."
```

### `tags` (list of strings)
Categorization tags
```yaml
tags:
  - data
  - kaggle
  - datasets
```

### `icon` (string)
Where the icon is: `<package>:<name>`, the package one of `@datalayer/icons-react` and
`@primer/octicons-react`, the name the icon's own in kebab case as that package names it —
`@datalayer/icons-react:odoo` (the Datalayer icons' `odoo.svg`, `OdooIcon`),
`@primer/octicons-react:mark-github` (`MarkGithubIcon`). A bare name is refused
(`agentspecs.marks`, `MARKS_SCHEMA`). A page draws it where it shows this entry — a list
of the catalogue, a call in the chat — and loads only that package.

### `emoji` (string)
Drawn where there is no icon; where there is neither, nothing is.

## Environment Variable Expansion

Use `${VAR_NAME}` syntax in `args`, `env` and `headers` for environment variable expansion:

```yaml
headers:
  Authorization: "Bearer ${KAGGLE_API_TOKEN}"

envvars:
  - KAGGLE_API_TOKEN
```

`${VAR_NAME:-default}` takes the default when the variable is unset or empty, as in a shell:
Bluesky's server is run from `${BLUESKY_MCP_SERVER_DIR:-/opt/mcp-servers/bsky-mcp-server}`,
where the runtime image builds it unless your machine has it elsewhere.

The `${KAGGLE_API_TOKEN}` will be expanded at runtime by consuming systems. A bearer that would
expand to nothing is refused before anything is sent: the server is not started, and the
reason names the variable.

## Complete Example

A remote server:

```yaml
# Copyright (c) 2025-2026 Datalayer, Inc.
# Distributed under the terms of the Modified BSD License.

id: kaggle
version: 0.0.1
name: Kaggle
description: Kaggle datasets, models, competitions, and notebooks access

transport: streamable-http
url: "https://www.kaggle.com/mcp"
headers:
  Authorization: "Bearer ${KAGGLE_API_TOKEN}"

enabled: false

envvars:
  - KAGGLE_API_TOKEN:0.0.1

tags:
  - data
  - kaggle
  - datasets

icon: "@datalayer/icons-react:kaggle"
emoji: "🏆"
```

A local server:

```yaml
id: tavily
version: 0.0.1
name: Tavily
description: Web search

command: npx
args:
  - "-y"
  - "tavily-mcp"

transport: stdio

envvars:
  - TAVILY_API_KEY:0.0.1
```

## MCP Server Hierarchy

```
MCP Server Specification
├── Basic Info (id, name, description, tags)
├── Where it is
│   ├── remote: url, headers (transport streamable-http)
│   └── local: command, args (transport stdio; or streamable-http with the url it listens at)
├── Environment
│   ├── envvars (required environment variables)
│   ├── env (variables to set for a local process)
│   └── sandbox_envvars (read by the code its tools write, in the sandbox)
└── UI (icon, emoji)
```

### Odoo, through the Datalayer server

The gateway serves Odoo in toolsets, and two of them are catalogue servers:
the `datalayer` server with one toolset each, the same hosted gateway and the
same bearer.

| Server | URL | Tools |
| --- | --- | --- |
| `odoo` | `https://mcp.datalayer.run/mcp?only=odoo` | 13: the session's context, account, settings and companies, the default company, models and fields, searches, reads, grouped aggregates, and creating, updating and deleting records of any model |
| `odoo-accounting` | `https://mcp.datalayer.run/mcp?only=odoo-accounting` | 61: invoices and vendor bills, journal entries, accounts and journals, trial balance and general ledger, partners and their ledgers, aged balances, taxes, assets, reconciliations, bank lines and feeds, exchange rates, lock dates, documents (UBL import, attachments), vendor payments, tax returns and the Belgian VAT close |

The two share no tool. Each spec lists exactly the tools the gateway registers
for its toolset, each classed as `datalayer` classes it, with the gateway's own
description of the tool above it.

`only=` asks for that toolset alone (and the gateway's always-on tools), where
the compact `?odoo` adds the toolset to the notebook surface `datalayer`
serves: an agent given several of these servers never sees one tool twice, and
an application's connection to the server is what the gateway checks the
session against. The gateway reaches Odoo with the `DATALAYER_ODOO_URL` and
`DATALAYER_ODOO_API_KEY` (and `DATALAYER_ODOO_DATABASE` where the host does
not name one) kept in the person's Datalayer environment; the runtime holds
only `DATALAYER_API_KEY`. Odoo's own access rights apply to that key.

### The Datalayer server is off by default

Every other server here reaches something *outside* Datalayer. `datalayer`
reaches this platform, and an agent running in a Datalayer sandbox already
has the notebook it was given — enabling it says "this agent should also act
on my other notebooks", which is a choice somebody makes rather than a
default they discover.

### Remote servers are reached by the runtime itself

`datalayer`, `odoo`, `odoo-accounting` and `earthdata` (the Datalayer gateway),
`huggingface` and `kaggle` name a `url` and `headers`, no command: the
runtime connects to the url over Streamable HTTP and sends the bearer with
every request. No local bridge (such as `npx -y mcp-remote`) is needed: a
runtime that cannot install packages reaches a remote server all the same.

The bearer rather than an OAuth flow, and deliberately: OAuth 2.1 with PKCE
is right for a person at a desktop client and wrong here, since it opens a
browser and waits for a consent screen to be approved. An agent runtime has
nobody at the keyboard, so it presents a credential it already holds — the
same token the Datalayer CLI and SDK use. A gateway that refuses the key
answers in a sentence, and the runtime says that sentence as the reason the
server did not start.

## Best Practices

1. **ID Format**: Use kebab-case (`kaggle`, not `Kaggle` or `kaggle_mcp`)
2. **Remote or local**: A hosted server names its `url` and `headers`; a server that runs on the
   runtime's computer names its `command`. Never a bridge from one to the other.
3. **Command**: Use full command names (`python`, not `py`)
4. **Args**: Break arguments into separate list items for clarity
5. **Environment Variables**: Always define required envvars in the `envvars` field
6. **Variable Expansion**: Use `${VAR_NAME}` syntax consistently
7. **Transport**: `stdio` for a local process; `streamable-http` for a server reached at a url
8. **Tags**: Use consistent tags for better categorization
9. **Description**: Be specific about what tools and resources the server provides

## Full Field Coverage

Required fields:

- `id`
- `version`
- `name`
- `description`
