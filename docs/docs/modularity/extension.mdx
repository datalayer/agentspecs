# Extension

Inheritance, with `extends`. Reach for it when the new spec **is** the old one
with changes — the relationship is "a kind of".

A child names one parent and overrides what it needs.

```yaml
# agents/cell-fixer.yaml
id: cell-fixer
extends: loop-base:0.0.1
model: "bedrock:us.anthropic.claude-sonnet-4-6"   # overrides the parent's
system_prompt_append: >-
  Fix the failing cell and prove the fix by running it.
```

- Single inheritance, and the chain may be **at most three deep**. A spec graph
  nobody can read is worse than a repeated field.
- A cycle is refused by name at generation time (`a → b → a`), not discovered at
  runtime.
- The reference may be versioned (`loop-base:0.0.1`) or bare (`loop-base`).

Extension carries *everything* the parent declares, subagent lists included —
which is the reason a specialist that only needs shared capability should
[compose a fragment](./composition) instead. See [Merge semantics](./#merge-semantics)
for what the child wins and what it appends to.

## Beyond agents

The same mechanism, and the same limits, carry the specs that are built on
other specs.

A **[Frame](../frames)** extends a Frame — a project's extends its
department's, which extends the company's:

```yaml
# frames/web-research.yaml
id: web-research
extends: datalayer:0.0.1
rules:
  - Report a claim only with the address of the page it was read on.
```

A **[Cog](../cogs)** extends an agent, and is equipped with Frames:

```yaml
# cogs/cog-crawler.yaml
id: cog-crawler
extends: worker-crawler:0.0.1
frames:
  - web-research:0.0.1
```

A **[Guard](../guards)** extends a Policy — the rules it verifies:

```yaml
# guards/sensitive-data-guard.yaml
id: sensitive-data-guard
extends: organization-baseline:0.0.1
category: policy-safety
stages: [in_flight, post_run]
check: No output contains a credential or personal data.
```

The Cog is the agent with what it says differently; the Frames are what it
works under; the Guard names the Policy and the check that it held (the
Policy is read through the catalogue, never merged in). All are resolved when
the catalogues are generated, so a runtime receives one flat spec.

## Overriding an application on stage

A [Battle](../battles)'s contestant and a [scene](../scenes)'s cast member
put an application of the catalogue on stage as it is. With `overrides`,
they say what **this appearance** plays differently — the same idea as
`extends`, a child saying what it changes, but for one place on stage, with
no new spec to write and nothing to version:

```yaml
# battles/deck-race.yaml
contestants:
  - id: blue
    app: deck-maker:0.0.1
  - id: red
    app: deck-maker:0.0.1
    overrides:
      model: "alibaba:qwen-max"      # the same application, another model
```

```yaml
# scenes/sales-and-accounting.yaml
cast:
  - member: sales
    persona: { name: Sales }
    overrides:
      model: "alibaba:qwen-max"
      instructions: Answer in one line, and name the figure's source.
```

| Key | What it overrides |
| --- | --- |
| `model` | The model the application answers with: a model of the [catalogue](../../models), `provider:name`. Checked as the spec is read. |
| `instructions` | Its instructions, whole. |
| `skills` | Its skills, whole: a list of skill ids. |
| `context` | Its context, whole. |

Nothing else of an application may be overridden on stage: what it is, its
interface, its rules and its tests stay its own. Any other key is refused as
the spec is read, with the four that are allowed.

On a contestant that plays a **scene**, the overrides reach every member of
the scene that is an application. The override is applied where the
application is played: a member played in the page answers with the model
it names; a member already at a deployment answers as it was shipped, and
the page says what was asked rather than pretend. Datalayer's own Battles
use it: in each race and challenge, Blue plays its application as it is and
Red plays it with Alibaba Qwen-Max.
